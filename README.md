## 这个项目想解决什么

美甲行业存在两个被长期忽视的真实痛点。

**商家侧**：中小美甲店主大多凭经验运营，看不懂后台数据、抓不住行业新趋势、面对差评不知如何复盘。平台后台只展示"什么发生了"，不解释"为什么发生"。决策依赖直觉，效率极低。

**用户侧**：打开点评或小红书想做美甲，最大的障碍始终是"戴到我手上是什么效果"。手型、肤色、甲长差异极大，图片滤镜不等于真实上手体验。这是美甲消费最大的决策摩擦，也是大量用户到店前犹豫不决的根本原因。

甲心助手试图同时切入这两个痛点，并通过数据飞轮将 B 端和 C 端的价值互相强化。

## 核心功能

### 1. 智能运营巡检（B 端）

每日自动扫描 5 大款式后台数据，识别 3 类异常：

- **异常下滑款式**：环比下跌 >25%，需要立即关注
- **转化偏低款式**：CVR < 2.5%，流量有但未转化
- **相对稳健款式**：作为对比基准，辅助判断异常程度

Agent 基于真实数据生成 v3.0 八段式分析，覆盖：诊断假设 / 数据观察 / 趋势判断 / 用户洞察 / 运营建议 / 不建议做什么 / 风险提示 / 下一步行动。结构化输出替代商家"凭感觉决策"的老路。

### 2. UGC 中心：外部信号 + 内部资产

**外部 UGC 信号**：综合多平台笔记数据，AI 自动识别行业趋势 Top 款式，帮商家看清"外面在流行什么"。

**内部 UGC 资产**：本店心智标签、差评话题聚类、款式 UGC 表现，帮商家看清"用户真实怎么评价"。

**飞轮机制**：UGC 数据 → AI 解析 → 反哺 Agent 系统提示词 → 商家决策更精准。外部信号和内部资产共同构成决策上下文，而不只是一个展示面板。

### 3. 商家内容池 + 店铺视觉 DNA（V2 核心创新）

商家上传作品图 → Claude Vision 自动打标签（风格/配色/季节/场合）→ 累积成内容池 → AI 综合归纳当前店铺视觉 DNA → DNA 反哺所有 Agent 对话。

这是产品的"内容飞轮"机制：商家上传越多，AI 越懂这家店，给出的建议越贴合门店实际定位，而不是泛泛而谈。

### 4. AI 美甲试戴（C 端 V1）

用户上传手图 + 款式图 → AI 在 10-15 秒内生成戴上效果图。

完整跑通的图像生成 pipeline：FLUX.1 Kontext Pro 负责图像编辑（保留手型、替换美甲款式），Claude Vision 负责理解款式图并生成精准提示词。

生成的试戴图可一键分享到商家内容池——形成"用户试戴 → 商家内容资产"的反哺链路，C 端的使用行为直接为 B 端创造内容资产。

### 5. 自然语言运营顾问

商家用大白话提问，Agent 基于真实后台数据 + UGC 信号 + 店铺 DNA 综合给出建议。

Prompt 工程经历了 3 轮迭代：v1.0 简单回答 → v2.0 结构化分析 → v3.0 八段式带行动优先级的决策框架。每一轮迭代都来自真实测试中发现的输出质量问题。

## 关键设计决策

### 1. 为什么用 mock 数据？

所有演示数据均为程序随机生成。这不是回避真实接入——这是产品验证策略。

商业数据接入需要平台 API 授权（美团 / 大众点评开放平台），学生作品集中不应假装"已接入"真实数据。真正可演示的是"AI 解析机制"，而不是"数据本身"。

**机制 > 数据**——这是我从这个项目里学到的最重要的产品认知。

### 2. 为什么 B 端用 Claude，C 端用 FLUX？

不同任务匹配不同模型，而不是用一个模型硬撑全部场景：

- B 端需要自然语言理解 + 结构化输出，Claude Sonnet 4.5 的推理能力是优势所在
- C 端需要图像编辑（保留原始手型 + 替换局部细节），FLUX Kontext 专为"图像编辑"而非"图像生成"而训练

中途测试过 Gemini 2.5 Flash Image 做 C 端。发现它在多色款式任务下存在 **statistical color collapsing**——会把参考图的多色款式坍缩为主色，5 指不同色彩的款式会被归一化成一种颜色输出。这个问题经过 4 轮 prompt 优化后仍然存在，最终判定为模型架构层面的限制，换到 FLUX 后问题消失。

### 3. 为什么强调"内容飞轮 > 数据飞轮"？

后台数据告诉你"发生了什么"，UGC 内容告诉你"为什么发生"。

单纯靠交易数据做的 AI 工具只是"高级数据看板"，缺乏解释性。真正的护城河是基于真实 UGC 的内容资产沉淀——每一条用户笔记、每一个差评标签，都是机器无法凭空生成的行业语境信号。

### 4. 为什么坚持脱敏合规？

整个产品中没有以任何方式冒充平台员工身份，没有直接调用未授权的平台数据，演示场景全部标注"模拟数据"。合规性是 AI 产品 PM 的基本素养，不是上线前的事后补救。

## V0 → V1 → V2 迭代路径

### V0：CLI 命令行 Agent

最早只是一个能用 Claude API 回答美甲运营问题的命令行工具（见 `nail_agent.py`）。

测试后发现：光有 AI 能力不够，商家需要"看得见数据的可视化界面"，才能产生信任感和使用动机。这个判断推动了向 V1 的演进。

### V1：Streamlit 双引擎平台（当前版本）

完整运营驾驶舱 + C 端试戴 + B/C 数据飞轮真实打通。这是当前 GitHub 仓库的状态。

### V2：路线图（已规划，未实现）

- AI 试戴效果一键预约同款门店服务（打通消费链路最后一公里）
- 多手型适配（短手指 / 长手指 / 不同肤色分场景推荐）
- 基于用户手型的 AI 款式推荐（个性化推荐层）
- 商家可配置"虚拟试戴优惠"激励真实到店转化

V2 需要推荐系统、关键点检测、商家配置后台等工程资源，超出当前版本的合理范围。项目主动将范围控制在 V1 完整落地——这本身也是一个产品决策。

## 踩坑与认知

这一节是整个项目中最值得分享的部分。

### 坑 1：多图任务的 statistical color collapsing

测试 C 端试戴时，Gemini 2.5 Flash Image 遇到 5 指多色款式，总是输出 5 指同色。经过 4 轮 prompt 工程优化（角色标记、形状分离、显式分指映射、chain-of-thought 分步骤描述）都未能解决。

**认知**：这是模型架构层面的限制，不是 prompt 能解决的。需要换"图像编辑专用模型"而非"图像生成通用模型"。

### 坑 2：通用生成模型 vs 图像编辑模型

Gemini / DALL-E 这类通用生成模型的工作方式是"看完输入后重新画"，没有"必须严格保留原图"的硬约束。FLUX Kontext 的训练目标是"局部编辑，保留 95%，只改动 5%"——架构上为图像编辑而设计。

**认知**：做 AI 产品时，模型选型 > prompt 调优。选错模型，prompt 调一万轮也救不了。

### 坑 3：AI 产品 PM 的最大陷阱是"再调一轮"

调试 C 端试戴时，我反复产生"再调一轮 prompt 就完美了"的想法——结果浪费了几个小时，输出质量始终在同一水平徘徊。

**认知**：识别"边际收益递减"的拐点是 PM 核心能力。60 → 80 分靠 prompt，80 → 95 分需要换工程方案，95 → 100 分需要训练专用模型。错配工具和目标，是 AI 产品最常见的错误。

### 坑 4：行业认知 > 通用 PM 经验

测试中我曾试图让 AI"保留用户原甲型 + 只换颜色"。但美甲行业的真实逻辑是：用户上传款式图 = 想做这个完整款式（甲型 + 颜色 + 图案是不可分割的款式包）。把甲型单独保留反而是错误的产品判断。

**认知**：做行业垂直 AI 产品，行业 know-how > 通用 PM 经验。没有行业语境的功能设计，技术再精准也是南辕北辙。

### 坑 5：输出稳定性 > 准确率

发现 Gemini 对同一组输入每次生成结果都有明显差异——这对"决策辅助类"产品是致命缺陷。用户问"戴上这款是什么样"，给出 5 个不同答案 = 失去信任。

**认知**：对决策类产品而言，stability > accuracy。可重复的结果是建立用户信任的根基，而不是锦上添花。

### 坑 6：完美主义陷阱

整个项目最大的教训：识别"什么时候该停"。一个 V1 真扎实 + 一个 V2 真规划，远胜于 5 个半成品。范围控制是产品能力，不是妥协。

## 快速开始

### 环境要求

- Python 3.10+
- macOS / Linux / Windows

所需 API Keys：

| Key | 用途 | 获取地址 |
|-----|------|---------|
| Anthropic API Key | B 端 AI 分析 | console.anthropic.com |
| Replicate API Token | C 端图像生成（必需） | replicate.com/account/api-tokens |
| Google Gemini API Key | 可选备用模型 | aistudio.google.com/apikey |

### 安装

```bash
# 克隆仓库
git clone [仓库地址]
cd jiaxin-assistant

# 安装依赖
pip install -r requirements.txt

# 配置 API Keys
cp .env.example .env
# 编辑 .env，填入你的 API Keys
```

### 运行

```bash
streamlit run home.py
```

浏览器自动打开 `http://localhost:8501`
